## 3. 对“纯RTAB-Map改造”原稿的核对

### 3.1 主建图节点与视觉里程计不是同一个节点

`rtabmap_slam/rtabmap`在当前RGB-D建图配置下需要里程计消息或相应TF。关闭subscribe_odom并不能自动创建视觉里程计。这不代表RTAB-Map必须依赖轮速或激光：`rtabmap_odom/rgbd_odometry`就是RTAB-Map自己的RGB-D视觉里程计组件，也是10月23日手推测试实际使用的组件。

当前恢复路线为RGB-D → rgbd_odometry → rtabmap，YOLO及语义点云为并行链。`pure_rtabmap_code_20261106`快照仍启动icp_odometry、订阅scan，属于激光方案，不能当作RGB-D旧手推版直接恢复。

### 3.2 ICP参数类型错误有原始日志支持

16:03运行记录了icp_odom退出250，原稿所述`wait_for_transform`布尔值与浮点秒数类型不符需要按接口定义处理。该项属于参数错误，不表示激光硬件失效。

### 3.3 静态TF不能简单归结为“没有代码发布”

此前本组`mapping_runtime.py`会读取mounts，发布到`/rtabmap_yolo/tf_static`；而ICP调试启动参数中存在使用全局`/tf`和`/tf_static`的情况。已有`base_link does not exist`日志支持接收端没有得到所需变换，但不支持“整个工程没有发布逻辑”的断言。应同时核对发布节点、话题范围和订阅重映射，不能只加全局静态TF掩盖范围不一致。

### 3.4 就绪流程不能靠取消使能检查修复

激光里程计并不必然要车辆先移动才能初始化。先排查TF、有效扫描及参数，再判断是否真有流程依赖。原稿将“成年人自己负责”作为删除首次A键松开检查的理由不适合工程报告；手柄使能和定位就绪是不同条件，应分别验证。当前手推基线完全不启动底盘控制，也不需要该手柄启动逻辑。

### 3.5 16:26只证明局部链路曾出数

16:26事件记录为复用`icp_odom`，未在该目录重新启动一个ICP进程。实际数据库Node总数53、保存优化位姿24、快照graph_poses=24，语义体素10661；最终状态仍为`failed`，原因为未通过首次手柄就绪条件。原稿中的“11节点、graph_poses=1”“16:20已有2975条有效里程计”与对应目录不一致；2975来自16:26的valid_odom计数。可以写“局部ICP—建图链路出现有效输出”，不能写“完整纯路线已通过”。
