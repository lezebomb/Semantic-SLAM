## 4. 语义发布与接收契约

表内 Image、CameraInfo、PointCloud2 均属于 `sensor_msgs/msg`；String 属于 `std_msgs/msg`。所有名称都是当前源码中的绝对话题名，不会自动跟随外层命名空间改变。

| 话题 | 消息／内容 | 发布节点 → 接收方 |
|---|---|---|
| `/semantic/label_image` | Image，mono8；0 背景，1—80 为 COCO 类别加一 | yolo_detector → semantic_projector／下游 |
| `/semantic/instance_image` | Image，mono16；单次观测编号 | yolo_detector → semantic_projector／下游 |
| `/semantic/paired_depth` | Image，保留此次配对深度 | yolo_detector → semantic_projector |
| `/semantic/paired_camera_info` | CameraInfo，此次配对内参 | yolo_detector → semantic_projector |
| `/semantic/image_annotated` | Image，bgr8，预测叠加图 | yolo_detector → 显示／记录方 |
| `/semantic/points_camera` | PointCloud2，相机系有效语义点 | semantic_projector → semantic_grid_node |
| `/semantic/pointcloud` | PointCloud2，单帧地图系语义点 | semantic_grid_node → 显示／下游 |
| `/semantic/map` | PointCloud2，累计语义地图 | semantic_grid_node → 显示／下游 |
| `/semantic/detector_status` | String，JSON：处理帧、预测耗时、时间差、实例预测 | yolo_detector → 观察／诊断方 |
| `/semantic/map_status` | String，JSON：TF、队列、体素等计数 | semantic_grid_node → 观察／诊断方 |

普通输出使用 Reliable、Volatile、depth 5。累计 `/semantic/map` 使用 Reliable、Transient Local、depth 1，下游按此配置才能在后加入时接收保留的地图。原投影器通过 `message_filters.TimeSynchronizer(..., 20)` 精确配对类别图、实例图、深度和内参。

类别图、实例图、标注图和配对内参的 header 使用配对深度时间；相机系和当前地图系点云也保留该时间。标注图的像素仍来自 RGB，RGB 与 Depth 的差值写在 detector_status 中。累计地图 header 是发布时刻，不表示所有历史点在该时刻采集。

累计语义地图只包含检测目标中具有有效深度的点，不是完整房间的几何重建。墙面或地面没有类别颜色，不能单凭这一点判断几何建图失败。

三个点云接口的字段均为：`x/y/z/rgb` 为 FLOAT32，`class_id/instance_id` 为 UINT32，每点 24 字节。坐标单位米；`rgb` 是打包显示色，不能作为普通浮点强度解释。点云 `class_id` 为 0—79，与类别图的 1—80 编码不同。`instance_id` 会循环使用，不能当作跨帧稳定身份；累计体素里也是观测编号。

TF 查询以深度采集时刻为准，目标 frame 默认 `map`，可通过本组参数调整。5 s 后仍取不到 TF 会丢帧，不回退到最新位姿。TF 队列容量 40，队列丢弃与超时分别计数。无有效语义点时不发布非空点云，不能只凭没有点云认定分割程序崩溃。

累计地图每 1 s 检查一次更新，仅 dirty 时发布。该定时器频率、每 3 帧抽 1 帧和单次推理耗时均不能替代实测整管线 FPS。

几何接口 `/map`（OccupancyGrid）、`/mapData`（MapData）、`/mapGraph`（MapGraph）由另行启动的 RTAB-Map 提供；后两者属于 `rtabmap_msgs/msg`。本组语义 live 入口不创建它们。`/semantic/map` 是点云，不能直接当作 Nav2 的二维 OccupancyGrid 使用。

## 9. ROS1、ROS2 与脚本归属

本组语义建图使用 ROS2 Humble。车上的 ROS1 Noetic 用于既有底盘通信，不要求语义建图改写为 ROS1，也不应删除这些底层依赖。

| 文件或组件 | ROS 版本／性质 | 职责和本组范围 |
|---|---|---|
| `yolo_rtabmap/semantic/*.py` | ROS2，使用 rclpy | 本组分割、投影和语义累积 |
| `yolo_rtabmap/launch/*.launch.py` | ROS2，使用 launch／launch_ros | 本组已核实的启动文件；不是 ROS1 launch |
| `run_live.sh`、`run.sh` | Bash 包装脚本，调用 ROS2 | 加载环境后用 ros2 launch 等启动本组程序 |
| `run_camera.sh`、`run_lidar.sh` | 旧部署中的 ROS2 驱动包装 | 相机／雷达配套；不是语义算法本体，当前不运行 |
| `run_handpush.sh` 等 | 本组旧 ROS2 测试配套 | 历史测试入口，与 ROS1 底盘驱动是不同部分 |
| `ros1_noetic` 容器 | ROS1 Noetic | ROS master 和 `/cmd_vel_to_mcu` relay |
| `rosserial_mcu` 容器 | ROS1 Noetic／rosserial | 通过串口与 MCU 交换底盘指令和反馈 |
| `ros1_bridge` 容器 | ROS1 ↔ ROS2 桥接 | 把 ROS1 反馈提供给 ROS2，连接两个通信系统 |
| `teleop/start-gamesir.sh` | Bash 包装的 ROS2 手柄入口 | 外部控制组接口；通过 ROS2 发指令，本组不启动 |
| `jetson-ros-start.sh`／systemd 服务 | 系统编排脚本，不是某个 ROS 节点 | 管理底层容器、桥接和串口的启动顺序；不由本组修改 |

判断陌生文件时优先看代码：`roslaunch/rosrun`、`rospy`、Noetic 环境通常属于 ROS1；`ros2 launch/ros2 run`、`rclpy/rclcpp`、Humble 环境属于 ROS2。Bash、Python 和 XML 是文件语言；launch 是启动方式，不能仅凭文件名判断 ROS 版本，ROS2 也支持 XML 启动文件。加载两套环境的桥接脚本要按实际用途单独判断。

本组后续统一从 ROS2 话题接收信息：MCU → ROS1 serial_node → ros1_bridge → ROS2 订阅者。读取编码器原始数组和获得 nav_msgs/Odometry 是两件不同的事；需要谁转换 odom、发布哪条 TF，仍待底盘方确认。未核实路径的其他组脚本只登记，不凭 ROS 版本猜归属或改动目录。


## 10. 能否不用手柄，直接自动运行

通信接口允许程序控制。现有约定是 ROS2 `/cmd_vel`（geometry_msgs/msg/Twist）经过桥接和 ROS1 relay 到 MCU；手柄只是一个速度指令来源。本轮确认了链路配置、运行进程和反馈接收，没有验证新的程序控制动作。

当前手柄使用 linear.x 和 angular.z，分别对应 m/s 和 rad/s。脚本只允许参数不超过 0.20 m/s、0.40 rad/s，这是 start-gamesir.sh 自己做的检查，不是 `/cmd_vel` 的全局限速。绕开手柄直接发布指令时不会自动继承它；现有 topic_tools relay 是普通转发，也没有实现限速或避障。MCU 超时停车行为尚未核验。

自动沿路线建图还需要连续的里程计和 TF、可用的障碍感知、定位/导航控制、速度限幅及输入过期时的停车处理。当前 `/odom`、实际 TF 和相机/雷达数据链都未验证，原始 encoder 数组不能替代这些条件。仅定时发送前进和转向消息，程序无法确认实际位移、路线偏差或障碍情况，不作为自动巡航方案。

后续优先接入导航组已有控制链，由其唯一最终速度输出接到约定接口，本组保持语义建图和证据记录职责。需要确认其他组的速度仲裁与当前底盘链是否已对齐，不能让多个程序同时争用最终速度话题。物理执行与停车仍需在获准的现场阶段验证。

当前车辆已断电；自动运行是后续待验证方案，不是现阶段已实现的功能。本轮没有新增自动驾驶代码、发布速度消息或调整底盘控制程序。
