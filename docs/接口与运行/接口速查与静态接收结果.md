# 接口速查与静态接收结果

2026-11-04，Asia/Shanghai。以下是车辆断电前的静止接收记录；用户随后告知断电，已停止远程查询。没有发送速度指令、启动驱动或开展移动建图。

## 1. 我们用 ROS2，为什么车上还有 ROS1

| 部分 | 版本／性质 | 作用 |
|---|---|---|
| 本组 `semantic/*.py`、`launch/*.launch.py` | ROS2 Humble | 分割、三维投影、语义累积与启动组合 |
| `run_live.sh` 等 | Bash 包装脚本，调用 ROS2 | 加载环境并启动本组节点 |
| `ros1_noetic`、`rosserial_mcu` | ROS1 Noetic | ROS master、串口 MCU 通信、底盘反馈和指令转发 |
| `ros1_bridge` | ROS1 ↔ ROS2 桥接 | 使 ROS2 程序可以接收 ROS1 底盘反馈 |
| systemd、容器启动脚本 | 系统编排 | 管理已有通信进程，不是语义算法 |

反馈链路为：底盘 MCU → ROS1 `/serial_node` → 桥接 → ROS2 订阅者。本组后续从 ROS2 接收即可。`.sh`、Python、XML 是文件语言；launch 是启动方式，不能只看文件名判断 ROS 版本。已核实的本组 launch 文件使用 `launch/launch_ros`，均是 ROS2。

## 2. 底盘哪些数据实际收到了

ROS2 Domain 0：21:13:05—21:13:18，建立订阅后的接收窗口约 10.05 s，发布节点均为 `/ros_bridge`。

| 话题 | ROS2 类型 | 接收结果 |
|---|---|---|
| `/encoder` | `std_msgs/msg/Float32MultiArray` | 178 条，约 19.50 Hz，数组长度 5 |
| `/chassis_charge` | `std_msgs/msg/Float32MultiArray` | 177 条，约 19.50 Hz，数组长度 3 |
| `/chassis_docking` | `std_msgs/msg/Bool` | 177 条，约 19.49 Hz，保存的样例为 false |
| `/chassis_initok` | `std_msgs/msg/Bool` | 看到了发布端，窗口内 0 条 |
| `/ultrasound_value` | `std_msgs/msg/Float32MultiArray` | 看到了发布端，窗口内 0 条 |

ROS1 在另一个约 8.03 s 窗口中也接到三项连续反馈，发布节点为 `/serial_node`。两个窗口不同，不用消息数之差计算丢包率。

`/encoder` 保存的原始样例为 `[0.0, 0.0, 5893723.0, 0.020943952724337578, 0.388700008392334]`。数组没有字段标签，也没有 Header。五项的含义和单位尚未确认，不能直接解释为位置、轮速或时间，更不能直接替代 `nav_msgs/msg/Odometry`。`/chassis_charge` 的三项同样尚未确认，暂不标成电压、电流或电量。

## 3. 恢复连接后如何只读接收

这些是 ROS2 终端命令，不需要启动本组分割或建图。车辆当前离线，不在本轮执行。

```bash
source /etc/jetson-ros/ros2-env.sh
ros2 topic echo /encoder std_msgs/msg/Float32MultiArray --once
ros2 topic echo /chassis_charge std_msgs/msg/Float32MultiArray --once
ros2 topic echo /chassis_docking std_msgs/msg/Bool --once
```

共享环境为 Domain 0、非仅本机通信、`rmw_fastrtps_cpp`。已有桥接可能在建立明确类型的订阅后才出现反馈发布端，因此只看一次 topic list 还不够。新程序按表中类型创建订阅即可，不需要自己再发布“测试消息”。

本地代码包还提供 `examples/read_chassis_feedback.py` 和 `read_semantic_output.py`。前者只允许订阅五个底盘反馈话题，默认 10 s 后退出；后者读取语义结果。两者均无速度发布器，且尚未上传到实车。

| 项目 | 观察结果 | 可以得出的结论 |

| `/tf`、`/tf_static` | Domain 0 和 77 两个约 10 s 窗口内均为 0 条，未见发布端 | 未得到实际坐标链，不能确认 map 到相机的变换 |

| `/scan` | 未发现发布端 | 尚未测到雷达帧率，也不能写已融合 |

没有深度帧，就没有执行“按深度采集时刻查 TF”的验证；这项应记“未验证”，不写成坐标变换已经通过或失败。

## 5. 后续只需补齐的内容

由底盘方确认编码器和电源数组的字段、单位，以及是否已有 ROS2 Odometry 发布程序；由传感器和定位负责方确认相机、雷达、标定 TF 与 map→odom→base_link 的发布责任。再对齐本组三个输入参数和 ROS 域，不改其他组程序，也不补未经标定的零 TF。

本组 live 默认 Domain 77，若接入 Domain 0 的共享数据，先在本组终端加载共享环境。两套候选相机话题和语义输出格式已放入总表；启动、保存等会改变运行状态的命令单列在详细说明中，不与只读接收命令混用。


## 6. 不用手柄是否就能自动建图

程序可以作为 `/cmd_vel` 的指令来源，但“能发速度”与“能自动沿路线建图”需要的条件不同。本轮仅验证了反馈接收，尚未验证程序控制动作、里程计、TF 和障碍感知链。

手柄脚本的 0.20 m/s、0.40 rad/s 限制只在该脚本中检查；直接发 `/cmd_vel` 不会自动继承这些限制，普通 relay 也不负责限速。后续由导航/底盘组统一确认控制、仲裁、限幅、输入过期停车和执行方向，再安排获准的现场验证。本组保持语义建图职责，当前不新增自动驾驶程序或速度发布命令。
