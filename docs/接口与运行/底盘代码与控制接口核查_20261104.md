## 2. 当前链路和旧launch的区别

```text
程序或手柄发布速度（本轮未发布）
└─ ROS2 Domain 0：/cmd_vel，geometry_msgs/msg/Twist
   └─ ros1_bridge 动态桥接（配置存在；本轮未建立速度发布端验证）
      └─ ROS1：/cmd_vel，geometry_msgs/Twist
         └─ /cmd_vel_to_mcu：topic_tools relay
            └─ ROS1：/cmd_vel_filtered
               └─ /serial_node → 串口 → MCU执行（本轮未验证执行）

MCU反馈
└─ rosserial_mcu容器中的 /serial_node
   ├─ /encoder → ros1_bridge → ROS2 /encoder
   │  └─ ROS2 /chassis_odom_node → /odom
   ├─ /chassis_charge
   ├─ /chassis_docking
   ├─ /chassis_initok
   └─ /ultrasound_value
```

主机串口是 `/dev/ttyUSB0`，容器映射为 `/dev/mcu`，波特率57600。主机没有 `/dev/mcu` 文件并不表示映射错误。当前桥接参数是 `--bridge-all-2to1-topics`，ROS2侧配置为Domain 0、非仅localhost。图中已看到ROS1的速度relay订阅和MCU串口节点接收端，控制链路的执行结果未测。

当前 `/cmd_vel_filtered` 的发布者是普通relay。话题名中的filtered不能证明速度已经限幅；旧 `vel_filters` 的代码存在，也不能证明它正在生效。`jetson-ros.service` 为active/exited的一次性启动服务，不能用该状态代替串口健康检查。

旧 `chassis.launch` 指向 `/dev/ttyACM0`，旧 `chassis_start.launch` 指向 `/dev/chassis`。后者还会启动参数初始化、手柄、速度滤波、旧雷达、里程计、导航、自动充电等组件。它们与当前容器串口和ROS2传感器组合不同，不应直接叠加启动。

## 3. 反馈与控制接口

| 接口 | ROS1类型；ROS2对应类型 | 用途与本轮状态 |
|---|---|---|
| `/encoder` | std_msgs/Float32MultiArray；std_msgs/msg/Float32MultiArray | 底盘原始轮侧反馈；两侧均未收到 |
| `/chassis_charge` | std_msgs/Float32MultiArray；std_msgs/msg/Float32MultiArray | 原始充电/电源相关数组；字段单位未确认，本轮未收到 |
| `/chassis_docking` | std_msgs/Bool；std_msgs/msg/Bool | 原始状态；含义未完整核实，本轮未收到 |
| `/chassis_initok` | std_msgs/Bool；std_msgs/msg/Bool | 初始化相关反馈；本轮未收到，不据0条判定初始化成功或失败 |
| `/ultrasound_value` | std_msgs/Float32MultiArray；std_msgs/msg/Float32MultiArray | 超声相关反馈；本轮未收到 |
| `/odom` | 当前发布端为ROS2 nav_msgs/msg/Odometry | ROS2里程计节点存在，但无实际消息 |
| `/cmd_vel` | geometry_msgs/Twist；geometry_msgs/msg/Twist | 速度输入；本轮仅查接收链和类型，未发指令 |
| `/cmd_vel_filtered` | geometry_msgs/Twist；geometry_msgs/msg/Twist | 当前relay到MCU的速度入口；不作为新的并行控制入口 |
| `/chassis_param` | std_msgs/Float32MultiArray；std_msgs/msg/Float32MultiArray | 底盘参数写入；仅登记，未调用 |
| `/charge_enable` | std_msgs/Bool；std_msgs/msg/Bool | 充电相关控制；仅登记，未调用 |

ROS2里程计源码将数组第0、1项用于两轮速度计算，第2项的差除以1000作为时间差，第3项作为轮速换算因子，第4项作为轮距使用。源码注释称左右轮定义需要调换，当前计算也对转向符号作了处理。这是接收端的解释与实现，尚未用对应MCU协议、已知距离和实际转向验证；不能据此宣布字段单位和方向全部确认。

旧参数初始化源码按“减速比、轮径、轮距、电机最大RPM、电机极数”构造5项 `/chassis_param` 数组。该顺序只说明旧主机代码如何发布，不证明当前固件接受范围或允许直接调用。

## 4. 本轮为什么不能确认底盘正常

22:07的ROS2约10秒窗口内，5个底盘反馈话题和 `/odom` 均为0条。22:09的ROS1约8秒复核中，原始反馈也均为0条。串口容器日志显示 `Returned short (expected 32 bytes, received 25 instead)`，之后持续出现 `Lost sync with device, restarting...` 和 `Requesting topics...`。

证据指向串口/MCU通信链路当时存在异常，不仅是ROS2话题发现问题。尚未确定是供电、线缆、板端状态或其他原因。本轮没有重启容器、重开串口、发送初始化或充电指令。21时曾收到约19.5 Hz的反馈，应与本轮异常分别保留。

ROS2里程计依赖 `/encoder` 回调发布 `/odom`，这能解释为什么进程仍在而消息缺失；当前还没有恢复后的接收结果，不能把解释当作故障已修复。实际进程参数为 `is_publish_tf:=false`、`odom_scale:=0.76`。0.76是其他组当时使用的参数，本轮没有标定或改动。

## 5. 后续能否不用手柄自动运行

从接口设计看，程序可以代替手柄成为速度指令来源。完整自主行驶还需要上层定位、规划和避障给出速度，并验证唯一的最终速度出口、限速、停止、断联处理和人工接管。仅按时间发布前进、转弯指令，无法据此知道实际距离或是否有障碍。

当前手柄脚本只允许线速度参数不超过0.20 m/s、角速度参数不超过0.40 rad/s；这只是该脚本的参数检查，不是所有 `/cmd_vel` 发布者都会继承的底盘限速。现有relay本身不提供这些限制，MCU的指令超时停车也未核实。

本轮结论是：主机侧有程序控制入口，但实际底盘反馈异常，不能确认控制执行正常，自动行驶尚不具备本轮验证依据。后续先恢复反馈和里程计，再由负责底盘/导航的小组共同核实控制、停车和避障；本组复用确认后的接口，不改写其程序结构。
